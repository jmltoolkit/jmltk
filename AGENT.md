Knowledge about this repository, for AI coding agents. This is jmltk — the
**JML-toolkit fork of JavaParser**, maintained by jmltoolkit (driving authors:
S. Weigl / "weigl" and co-workers). It extends the upstream JavaParser with
JML (Java Modeling Language) parsing, located in `javaparser-core-*` +
`jmlparser-*` modules.

Primary working directory used for active development: `/home/weigl/work/javaparser`

## What this repo is

- A fork of https://github.com/javaparser/javaparser with a JML grammar added
  on top of JavaCC (`javaparser-core/src/main/javacc/java.jj`).
- JML comments (`//@ …`, `/*@ … */`) are lexed with dedicated token kinds, then
  post-processed by `com.github.javaparser.jml.JmlProcessor` (activated via
  `ParserConfiguration.setProcessJml(true)`). The processor turns
  `JmlDocStmt`s into real JML AST nodes.
- The repo is the base for contracts, JML expressions/clauses/statements, the
  JMLdoc support, and — recently — KeY-style **proof scripts in assert
  statements** (`assert expr \by { … };`).

## Modules (Gradle root project: `jmlparser-parent`, repo name `jmlparser-*`)

- `:jmlparser-core` — the parser + AST (this is what upstream calls javaparser-core).
- `:jmlparser-core-generators` — the visitor/metamodel code generators (ported from upstream).
- `:jmlparser-core-metamodel-generator` — generator for `ast.metamodel.*MetaModel` classes.
- `:jmlparser-symbol-solver-core` — symbol solver.
- `:jmlparser-core-testing` — the main test module (tests live under
  `javaparser-core-testing/src/test/java/`, Gradle name `:jmlparser-core-testing`).
- Others: `jmlparser-jml-tests`, `jmlparser-core-serialization`,
  `jmlparser-core-testing-bdd`, `javaparser-key-testing`, `tools`.

Note the asymmetry: **source dirs are `javaparser-core/…` but Gradle module
names are `jmlparser-*`.** Always use the `jmlparser-` names on the command
line (`./gradlew :jmlparser-core:compileJava`), and the `javaparser-` prefixes
for paths.

## JML processing pipeline (important mental model)

1. Source is lexed; `//@`/`/*@ … */` produce `JML_LINE_COMMENT`/`JML_*_COMMENT`
   tokens. With JML processing on, comments are kept as `JmlDocStmt` nodes.
2. `JmlProcessor` (`javaparser-core/src/main/java/com/github/javaparser/jml/JmlProcessor.java`)
   rewrites the tree: method-level comment blocks are extracted and re-parsed
   with the dedicated start rule `JmlMethodLevelStart` (in `java.jj`) via
   `JavaParser.parseJmlMethodLevel(String)` (which switches the lexer to
   `JML_MULTI_CONTRACT` state internally with `enableJml`).
3. `ArbitraryNodeContainer` (`ast.jml.ArbitraryNodeContainer`) holds the parsed
   JML statements (`JmlStatement` subclasses: `JmlExpressionStmt`,
   `JmlGhostStmt`, `JmlUnreachableStmt`, …), which are then spliced into the
   source tree at the original comment positions.

So: any statement-level JML grammar lives in `JmlMethodLevelStart` (java.jj
≈ line 7017) and the `JmlStatement*` productions; it is **only reachable from
that entry point**, which makes grammar changes to it isolated from plain-Java
parsing.

## Grammar + generated parser

- Grammar: `javaparser-core/src/main/javacc/java.jj`
- Generated parser: `javaparser-core/build/generated-src/main/javacc/com/github/javaparser/GeneratedJavaParser.java`
  (regenerated by the `compileJavacc` Gradle task when `java.jj` changes;
  do not hand-edit generated sources).
- New tokens must be declared with a dedicated lexer rule. Token-kind integers
  are auto-assigned in declaration order; do not reorder existing rules.
- **`TokenTypes.java` gotcha:** every public token kind must be classified in
  `com.github.javaparser.TokenTypes#getCategory(int)` (KEYWORD/SEPARATOR/
  OPERATOR/…). Forgetting a new keyword token throws
  `AssertionError: Unable to categorise token kind N` at runtime and also
  breaks `TokenTypesTest`. (FROM_GOAL = 179 was added as a KEYWORD.)

## Code generation workflow (do NOT hand-edit generated files)

Regeneration pipeline (one-shot: `scripts/run-generators.sh`):

```
./gradlew :jmlparser-core-metamodel-generator:run   # rewrites metamodel/*MetaModel.java
./gradlew :jmlparser-core-generators:run            # rewrites visitors (Clone, Equals, Modifier, HashCode, Observer, …),
                                                    # ObservableProperty, JavaToken kinds
./gradlew spotlessApply                             # normalizes headers + formatting
./gradlew :jmlparser-core:compileJava               # verify
```

Key facts:

- The generators write the **upstream JavaParser license header** into output
  files; spotless (`licenseHeaderFile("$rootDir/gradle/header")` in
  `build-logic/src/main/kotlin/buildlogic.java-conventions.gradle.kts`)
  rewrites it to the jmltoolkit header. Run `spotlessApply` after every
  generator pass, otherwise you get ~190 files of pure header churn.
  (History shows this churn, then collapse, after each pass — it is normal.)
- **Bootstrap deadlock:** `:jmlparser-core-generators:run` needs
  `jmlparser-core` to compile, but the generator's previous output may break
  the compile (e.g. a generator bug). In that case hand-fix the offending
  generated file so core compiles, then re-run the generator (it
  deterministically overwrites the hand-fix with the correct output — but keep
  the generator fix!).
- Generators operate via `addOrReplaceWhenSameSignature` and clear/rebuild
  method bodies for the node’s properties; hand-written member order is
  canonical (`@Generated` bodies in deterministic order).
- `CloneVisitorGenerator` (in `:jmlparser-core-generators`) was patched to
  unwrap optional **non-node** attributes via `.orElse(null)` when passing
  them to the cloned-node constructor (see `JmlProofCmd.kind`).
- Metamodel nodes are registered in
  `jmlparser-core-metamodel-generator/…/MetaModelGenerator.ALL_NODE_CLASSES`.

Workflow used for this feature branch (do this):

```
# after grammar/AST/code changes:
./gradlew :jmlparser-core-metamodel-generator:run && \
./gradlew :jmlparser-core-generators:run && \
./gradlew spotlessApply && \
git diff --exit-code   # generators are deterministic; no diff => idempotent
```

## The proof-scripts feature (`\by` in assert) — current state

Branch `weigl/proofscripts` → draft PR **#77**

GitHub: https://github.com/jmltoolkit/jmltk/pull/77 (base `main`, head `weigl/proofscripts`).

### Grammar (java.jj)

- Token `<BY : "\\by">` (line 281); `<FROM_GOAL : "\\from_goal">` (line 422).
- `JmlStatement` first alternative (≈ line 7069): `(<JML_ASSERT> | <ASSUME> | …)
  expr=Expression() ( <BY> script=JmlProofScript() | {} ) ";"`.
- Productions: `JmlProofScript` (line 7123), `JmlProofCmd` (line 7154),
  `JmlProofArgList`/`JmlProofArg` (line 7204), `JmlProofCmdSuffix`,
  `JmlProofCmdCase` (line 7216).
- `obtain` is NOT a keyword: it is recognized contextually via semantic lookahead
  (`LOOKAHEAD({ getToken(1).kind == IDENTIFIER && "obtain".equals(...) })`).
- `JmlProofCmdSuffix()` returns `JmlProofScript`: `null` for `;`, the nested
  script for `<BY> script` (a command followed by a nested `\by` script).
- Brace scripts allow empty bodies (`{ }`); the command loop is a `*`.

### ⚠️ The single most important grammar lesson on this branch

Do **not** write a nested syntactic LOOKAHEAD inside a rule that itself is
selected by an outer syntactic LOOKAHEAD, e.g.:

```
[ LOOKAHEAD(<BY>) script=JmlProofScript() ]   // BROKE parsing
```

JavaCC **drops the nested guard** when simulating the enclosing lookahead, so
the simulation parses `JmlProofScript` without consuming `\by` first, fails on
the following token, and the whole branch gets rejected (fall-back to the
modifiers branch → `Encountered unexpected token: "assert"`). The fix that
works:

```
( <BY> script=JmlProofScript()
| {}
)
```

i.e. fold the guard into a deterministic choice whose first token is part of
the simulated expansion. See commit `a8ae0d260` for the full story.

### AST (`com.github.javaparser.ast.jml.proof`)

Nodes extend `Node` directly (design decision: *no* `isX/asX/toX/ifX` casting
for these):

- `JmlProofScript` — required `NodeList<JmlProofCmd> cmds` + `NodeList<JmlProofCmdCase> cases`.
- `JmlProofCmd` — either an *obtain* command (`type`, `var`, `kind`, `value`)
  or a *general* command (`name`, `args`). `kind` is the inner enum
  `JmlProofCmd.ObtainKind` (`EQUAL("=")`, `SUCH_THAT("\\such_that")`,
  `FROM_GOAL("\\from_goal")`, with `jmlSymbol()`), stored as a **plain
  (non-node) `Optional` attribute**. Optional nested `JmlProofScript suffix`.
- `JmlProofArg` — optional `SimpleName label` + required `Expression expr`.
- `JmlProofCmdCase` — optional `StringLiteralExpr label` + `NodeList<JmlProofCmd> cmds`;
  `null` label means both `default:` and label-less `case:`.

The script slot lives on `JmlExpressionStmt` as `@OptionalProperty JmlProofScript script`;
3-arg constructors kept for back-compat; `@AllFieldsConstructor` lists `jmlTags` first.

`ObservableProperty` gained `ARGS/CASES/CMDS/SCRIPT/SUFFIX/VAR`.

### Printing (`DefaultPrettyPrinterVisitor`)

- `visit(JmlExpressionStmt)` prints ` \by <script>` before the terminating `;`
  (inside `wrapInJmlIfNeeded`).
- `JmlProofScript`: single bare command without cases prints without braces
  (`\by oss;`); otherwise `{ … }`. Mixed cmds+cases print cmds first.
- `JmlProofCmd`: `obtain <type> <var> <kind-symbol> [value]` or `name args…`;
  terminator `;` unless a nested `\by` suffix is present (bare nested form
  needs `;;`).
- `JmlProofCmdCase`: `case "label": …`; null label prints `case:`.

### Validated behavior (tests: `JmlProofScriptTest`, 4 green)

The user’s reference input round-trips:

```
//@ assert (\forall int x; x != mx; 2 * count(a, k+1, x) <= k+1 - mc) \by
//@   { oss; obtain int x \from_goal; expand on: "self.count(a, k_0 + 1, x)";
//@     macro "nosplit-prop"; instantiate var:"x" with: x; auto classAxioms:false; };
```

### Known accepted limitations (do not "fix" without talking to maintainers)

- KeY postfix assert labels (`assert LAB: e;`) NOT supported — JMLtk uses prefix
  labels only.
- `default:` and label-less `case:` both yield a `null` label.
- Mixed cmds+cases lose interleaving in the AST (two lists).
- Bare `\by oss;` needs `;;`; only the brace form is a round-trip target.
- `assert e \by;` (script-less `\by`) is not supported.

## Repository conventions & gotchas

- **Branch/PR workflow (explicit user instruction):** commit regularly, push
  to `origin` (jmltoolkit/jmltk) as `weigl/<feature>`, open/update a draft PR.
  `gh` is authenticated as `wadoon`.
- **`javaparser-core-testing/src/test/resources/com/github/javaparser/bulk_test_results/javaparser_test_results_javaparser_symbol_solver_testing_src_test_java.txt`
  is a pre-existing untracked artifact — NEVER commit it.** Keep it untracked.
- Pre-existing test failures: the full `:jmlparser-core-testing` suite has
  ~378 failures on `main` (mostly `printer.lexicalpreservation` /
  `IssueNNNNTest`). When verifying no-regression, compare the *set of failing
  classes* before/after (e.g. stash → run → diff) rather than absolute counts.
- Test module disk layout: tests under
  `javaparser-core-testing/src/test/java/com/github/javaparser/…` (path prefix
  `javaparser-`, Gradle name `:jmlparser-core-testing`).
- When adding grammar tokens/terms, also check `TokenTypes.java` (see above).
- Spotless is the formatter (palantirJavaFormat + importOrder + licenseHeader);
  run `./gradlew spotlessApply` before committing generated/edited Java.
- `./gradlew` runs may use a configuration cache and reuse tasks; use
  `--no-configuration-cache` (or change inputs) if results look stale.
